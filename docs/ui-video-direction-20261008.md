## 结论

保留三维地图主导、深绿与暖纸色、银杏页边纹样；优先调整对话与地点的连续操作，不另换一套主题。比赛只提交视频不代表可以用假响应、隐藏未知数据或只做不可交互的样片。

## 源码额外揭示的问题（不是浏览器复现结果）

- app/explore/main.js 的结果卡进入 showPlace 后用地点详情替换聊天，返回入口指向地点列表；建议保留回答上下文与滚动位置。
- explore.css 中顶部输入与左侧面板分离，聊天使用较窄面板和多层内边距；建议仅扩大聊天态，不一律扩大全部面板。
- main.js 在流式事件中重绘对话并滚到底部；有阅读位置跳动风险，需真实流式测试。应增量更新当前回答，仅当用户已在底部时跟随。

## 推荐方向：校园导览式任务面板

页面只保留一个主要任务区。探索态仍是地图与顶部短入口；对话展开时，原输入控件归入侧面板底部，不额外复制一个输入框。推荐卡的“在地图看”只改变镜头与标记，不关闭回答；“详情”进入同面板子页，可返回这次回答。

| 状态 | 主要内容 | 地图行为 |
| --- | --- | --- |
| 探索 | 分类与短提问入口 | 可自由拖动；沿用可停止的漫游规则 |
| 对话 | 简短回答、最多三项候选、底部输入 | 保持当前位置，不随生成文字转动 |
| 定位 | 选中候选，高亮与其他候选可比较 | 用户点击后一次可中止的平滑定位 |
| 详情 | 身份、地址/楼层、时段、相关商品 | 保持选中；返回恢复回答与滚动位置 |

### 第一轮：操作连续性

1. 统一提问与回答位置；聊天态桌面宽度先试 400–440px。
2. 地图定位不替换回答，地点详情返回原上下文。
3. 筛选默认折叠，桌面首屏目标至少看到三条简短结果。
4. 用户向上阅读时不强制滚底；以“新回答”按钮提示。

### 第二轮：字体和内容层级

1. 宋体仅用于少数页面标题，正文与按钮统一清晰无衬线字体。先以标题24–28px、正文16px、辅助13–14px试排；最终按录制缩放验收，不机械套数字。
2. 每条回答不再反复展示大品牌标题；先短结论，再店铺选择。卡片减少嵌套边框和装饰徽章。
3. 三层文字：名称/结论最醒目，价格/楼层/营业时间次之，来源按需查看；预算、时段、位置不确定性不能隐藏。
4. 银杏与纸纹留在边缘、空态，不铺在正文下面。绿色只承担选中、主操作与地图关联，避免所有东西同样抢眼。

### 第三轮：录屏节奏

1. 用同一段真实流程对比改前改后：提出用餐需求 → 比较候选 → 定位楼栋 → 查看菜单 → 修改一个条件。
2. 若菜单价格或耗时不足，就展示限制并换有证据的案例，不伪造“满足条件”。
3. 地图移动只发生在用户选择目标时；定位后留出阅读时间。减少动态设置仍有效。
4. 在真实16:9录制画布检查字幕、卡片和热点互不遮挡；视频缩小至720p再看文字是否可读。窄屏同步检查，不能为视频牺牲正常使用。

## 验收及限制

- 连续完成提问、比较、定位和返回，不丢回答、不重置滚动、不出现重叠输入框。
- 正常缩放下的桌面与窄屏都能访问完整列表；没有价格依据就不显示已满足预算。
- 流式生成、失败重试、取消、账号切换须单独测试，当前审查没有覆盖。
- 截图提示小字、浅色文字和密集控件可能影响可读性；尚未测量对比度或完成键盘/屏幕阅读器测试，不宣称可访问性合规。
- 实施前按 CLAUDE 明确范围；不动模型接口、业务数据与几何。实施后执行项目既有语法/API/行为回归，再保存同流程截图。此文档不是新产品版本交付。

## 本次纠错总结

用户已认可整体布局，不能将局部不好用解释为需要重做全站。所谓“AI味”应落到可观察问题：重复标题、重叠卡片、装饰超过内容、入口与结果分散。先改善这些，再评价视觉风格；生成概念图、代码通过和真实使用体验分别验收。
