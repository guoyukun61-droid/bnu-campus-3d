## 2. 最终关系框架

```text
物理建筑 building（叫什么、用途、模型身份）
  └─ 楼层 floor（在第几层；没有数字楼层就不造floor）
       └─ 场所 poi（新三、新四等业务入口）
            ├─ 窗口 outlet（真正要“换一家”的对象）
            │    └─ 菜单组 menu_group（稳定的证据组织）
            │         └─ 商品 item（菜名、规格、单价及来源）
            └─ 原楼层集合 collection（保留旧Shop来源，不当成独立窗口）

派生窗口 ──derived_from──> 原楼层集合
商品 ──offered_by──> 真实窗口
旧来喜福POI/Shop ──same_as──> 有效POI/Shop
独立两店 ──adjacent_to / west_of / east_of──> 独立两店
店铺 ──located_in_part──> 建筑的北面 / 南面西侧
店铺 ──member_of / ordered_along──> 名录区域
```

关系是有类型的，不能互换：

| 类型 | 主体→对象 | 本项目例子 | 是否提供精确几何 |
|---|---|---|---|
| contained_in | 子实体→容器 | 朱家小馆→新四→4层→新乐群 | 否，仅明确包含 |
| listed_in | 商品→菜单组 | 某规格鸡肉饭→对应照片菜单组 | 否 |
| offered_by | 商品→窗口 | 菜品→6号窗口 | 否 |
| derived_from | 派生窗口→原集合 | 新三窗口→原三层菜单集合 | 否，来源关系 |
| same_as | 旧身份→有效身份 | 旧百度来喜福→laixifu | 否，身份关系 |
| adjacent_to | POI→POI | 蜜雪→肯德基（并保存反向） | 否，距离未知 |
| west_of / east_of | POI→POI | 优果荟→天猫，反向为east_of | 否，仅方向 |
| located_in_part | POI→building | 来喜福→学五，building_part=north | 否，部位而非店门 |
| member_of | POI→area | 店铺→小吃街主排 | 否，名录不是测绘边界 |
| ordered_along | POI→area | 小吃街组内北到南序号 | 否，不可等距生成点 |
| relative_to | POI→building | 仅知参照建筑的其他旧记录 | 否，不等于在楼内 |

果荟/天猫这一对改用已确认东西关系，旧分组中两者北南顺序不继续作为有效排序；其他时间表分组保持。原始记录中的旧值仍在，未删除或改写。

## 5. 文件与接口如何使用

整理包：[data.2入口](../data/life/organized/data-1.20.0-data2-20261008-r1/README.md)。21个文件，共约4.697 MiB；只在本机私有目录，不通过HTTP静态发布。

- `confirmed-windows.csv`：本批20窗口、楼层、原集合、确认来源、未知时段。
- `menus.csv`：560条商品及精确窗口/菜单组归属，模拟逐条标记。
- `shops-roster.csv`：38条时间表名录，按组和楼层看缺口。
- `buildings.csv`：234体块的名称、简介、来源、状态；先看83个有名对象。
- `relations.json` / `snapshot.json`：完整可机读关系；`review-issues.csv`是剩余问题。
- `inspect.ipynb` / `manifest.json`：复算断言与SHA-256清单；原库不能用此包覆盖。

后端仍为Python＋JSON读取层＋旧SQLite适配，没有新数据库服务。调用顺序：原JSON与旧SQLite→百度标准化→已批准贡献→官方补充→身份归一→本次人工确认→菜单/关系API。

新版接口示例（以新代码启动服务后才生效）：

```text
GET /api/app/v2/entities/poi/canteen-3/children
GET /api/app/v2/entities/outlet/outlet-xinlequn-3-005
GET /api/app/v2/entities/outlet/outlet-xinlequn-3-005/children
GET /api/app/v2/menu-groups/menu-group-xinlequn-3-005/items
```

旧`get_place`仍平铺菜单以兼容旧UI，但附带menu_groups/outlets/outlet_id及窗口时段字段。推荐现在按实际outlet_id去重，不再把整层当一家。“换一家”应传outlet_id而非楼层POI。

来喜福旧ID及旧Shop可转向有效身份；如果以后旧Shop下有菜单，读取时保留Item和原shop_id，别名Shop记录source_poi_id，商品的业务outlet_id转向有效窗口，避免归档后把菜单藏掉。源库仍未合并。存在既有冲突别名/循环不强行覆盖；以后若窗口时段需要正式写入，可另行设计经批准的存储变更，不把派生导出当写入源。

1. 果荟与天猫：一起点选所在楼栋或两店入口；不用再确认是否相邻及谁在东。
